# M36 v1.0.0 release failure and rollback runbook

**Tracked ID:** `RLS-REG-ROLLBACK`

**Owner:** project owner acting as release operator

**Scope:** tag, GitHub release, npm publication, deprecation, rollback, and forward fix

This runbook does not authorize a release. Use it only after the M36 candidate, package, CI, live,
and publication gates have passed and the project owner has explicitly authorized the tag.

## Invariants

- Never overwrite an npm version or move a tag after that version has been published.
- Never publish locally. Only `.github/workflows/release.yml` may publish.
- Treat `npm view agent2linear@1.0.0` as the source of truth for whether npm accepted the version.
- Preserve failed workflow logs and the exact candidate SHA before retrying or fixing forward.
- Prefer deprecation plus a forward fix over unpublishing a version users may already have fetched.

## Bad tag before npm publication

Owner: release operator.

1. Cancel the release workflow if it has not reached `npm publish`.
2. Verify `npm view agent2linear@1.0.0 version` reports that the version does not exist.
3. Record the bad tag SHA and failure reason.
4. Delete the bad remote tag, fix and verify a new candidate commit, and create a new annotated
   `v1.0.0` tag only after explicit owner authorization.

If npm already reports `1.0.0`, do not delete or move the tag; use the published-release path below.

## Failed publish workflow

Owner: release operator.

- If npm does not contain `1.0.0` and no source change is required, rerun the failed workflow on the
  unchanged annotated tag so tag, candidate SHA, and provenance remain identical.
- If a source or workflow change is required and npm does not contain `1.0.0`, follow the bad-tag
  procedure and create a newly verified candidate before retagging.
- If npm contains `1.0.0`, treat publication as successful even if a later workflow step failed. Do
  not retry `npm publish`; finish registry/GitHub verification and repair only the missing metadata.

## Published release is defective

Owner: project owner decides; release operator executes.

1. Capture the npm integrity/provenance, GitHub tag SHA, failing behavior, and affected versions.
2. Publish a visible warning in the GitHub release and repository issue tracker.
3. Deprecate the defective version with an actionable replacement message when appropriate:

   ```sh
   npm deprecate agent2linear@1.0.0 "Defective release; use <replacement-version>"
   ```

4. Restore `latest` to the last known-good version only when that is safer than leaving the major
   release selected:

   ```sh
   npm dist-tag add agent2linear@<last-good-version> latest
   ```

5. Fix forward with a newly verified patch release, normally `1.0.1`. Never reuse `1.0.0`.

Unpublishing is an exceptional owner decision subject to npm policy and dependency impact. It is not
the default rollback mechanism.

## GitHub release or metadata failure after npm publication

Owner: release operator.

- Create or repair the GitHub release against the existing immutable `v1.0.0` tag.
- Use the already published package integrity and exact tag SHA in the release notes.
- Do not republish npm solely because GitHub release creation or notes failed.

## Closeout evidence

Record all of the following in the release issue or PR:

- incident and decision owner;
- original candidate SHA and tag SHA;
- npm version, integrity, provenance, and current `latest` dist-tag;
- deprecation or dist-tag commands executed;
- replacement version and its verification evidence; and
- confirmation that GitHub and npm again identify the intended exact source.
